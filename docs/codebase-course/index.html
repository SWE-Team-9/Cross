How the Cross app is wired

This course explains the current Flutter codebase from the top down. The app starts in lib/main.dart, builds the root widget in lib/app/app.dart, routes traffic in lib/app/router.dart, and wires dependencies in lib/core/di/injector.dart.

The practical goal is not theory. It is to help you answer questions like: Where does a new feature belong? Why is a page not opening? Which dependency should I register? Why does Windows behave differently?

Flutter flutter_bloc go_router get_it dio Windows support
Core idea

The app behaves like an airport. main.dart opens the building, app.dart sets the control desk, router.dart sends travelers to the right gate, and injector.dart makes sure each desk has the tools it needs.

Best first files to inspect

lib/main.dart, lib/app/app.dart, lib/app/router.dart, lib/core/di/injector.dart, lib/core/config/app_config.dart, and windows/runner/main.cpp.

Current reality on dev

Some areas are real and wired. Some are still placeholder or mock-driven, especially the home screen and several routes.

Module 2

Startup flow: from app launch to first screen

This is the most important path in the app. If startup fails, everything above it becomes irrelevant.

The boot sequence

1

Flutter binds itself to the platform

WidgetsFlutterBinding.ensureInitialized() makes sure Flutter is ready before async setup starts.

2

Dependency setup runs

setupDependencies() registers storage, networking, repositories, use cases, cubits, and services.

3

The root widget is mounted

runApp(const App()) starts the app tree.

4

Router chooses the first visible route

The current initial location points to the auth splash page.

Code ↔ English

lib/main.dart
import 'package:flutter/material.dart';
import 'app/app.dart';
import 'core/di/injector.dart';

void main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await setupDependencies();
  runApp(const App());
}
  1. Import the Flutter UI toolkit.
  2. Import the root app widget.
  3. Import the file that prepares the shared services.
  4. Before doing anything else, make sure Flutter is fully ready.
  5. Wait for the dependency setup to finish. This matters because later screens expect those objects to exist already.
  6. Finally, attach the app to the screen.

Module 3

The router map: how screens are chosen

The router is the building directory. It knows which path opens which page, and which pages need extra data before they can build.

Safe static routes

/home, /feed, /search, /library, and /upgrade are straightforward fixed paths.

Dynamic routes

/profile/:handle, /followers/:handle, and /following/:handle require a path value. If the handle is wrong or missing, the page will still build with bad input.

Code ↔ English

lib/app/router.dart
final GoRouter router = GoRouter(
  navigatorKey: _rootNavigatorKey,
  initialLocation: AuthRoutes.splash,
  routes: [
    ...AuthRoutes.routes,
    GoRoute(
      path: AppRoutes.home,
      name: 'home',
      pageBuilder: (context, state) => const NoTransitionPage(
        child: MockHomePage(),
      ),
    ),
  ],
);
  1. Create one shared router object for the whole app.
  2. Give it the root navigator key so navigation can be controlled centrally.
  3. Set the first location to the auth splash page.
  4. Import all auth routes in bulk.
  5. Define the home route separately and map it to MockHomePage().
  6. The current home is still a mock page, which is important when you debug “why is this dummy content showing?”

Module 4

Dependency injection: who builds the shared objects

injector.dart is the warehouse manager. It prepares the objects the app will reuse so features do not create their own copies everywhere.

Code ↔ English

lib/core/di/injector.dart
if (!getIt.isRegistered()) {
  getIt.registerLazySingleton(
    () => DioClient(
      baseUrl: ApiConstants.baseUrl,
      secureStorage: getIt(),
      cookieJar: cookieJar,
    ),
  );
}

if (!getIt.isRegistered()) {
  getIt.registerLazySingleton(
    () => SocialRepo(getIt().dio),
  );
}
  1. Before registering something, check whether it already exists.
  2. Create one shared DioClient lazily. “Lazy” means it is built only when first needed.
  3. That client uses the base API URL, secure storage, and a cookie jar.
  4. Then create one shared SocialRepo.
  5. The repository depends on the already-registered Dio client.
  6. This pattern keeps networking consistent across the app.

Storage objects

FlutterSecureStorage and the custom SecureStorage wrapper are registered early.

Network objects

DioClient becomes the shared HTTP gateway to the backend.

Feature objects

Repos, use cases, and cubits are registered after their dependencies are ready.

Feature modules: what the app can do

The app is split into feature areas. That keeps responsibilities separate and makes debugging more local.

Auth

Upload + Track management

Upload picker and track-management flows exist, and some behavior can run in mock mode depending on config.

Code ↔ English

lib/core/config/app_config.dart
static const String apiUrl = String.fromEnvironment(
  'API_URL',
  defaultValue: 'http://10.0.2.2:3006',
);

static const bool useMockTrackManagement = bool.fromEnvironment(
  'USE_MOCK_TRACK_MANAGEMENT',
  defaultValue: false,

  1. Read the API base URL from a compile-time environment variable.
  2. If no variable is supplied, fall back to a default local backend address.
  3. Read a feature flag for mock track management.
  4. If enabled, the app can use fake behavior instead of real backend behavior for that area.
  5. This is useful during development, but it can also confuse you if you forget mock mode is on.

Module 6

The Windows layer: where desktop-specific issues start

Flutter apps are cross-platform, but the desktop launch layer still matters. Windows has its own runner, build files, and package behavior.

Build metadata

windows/CMakeLists.txt still uses the generic project and binary name Iqa3.

Runner title

windows/runner/main.cpp also creates the window with title Iqa3.

Code ↔ English

windows/runner/main.cpp
flutter::DartProject project(L"data");

FlutterWindow window(project);
Win32Window::Point origin(10, 10);
Win32Window::Size size(1280, 720);
if (!window.Create(L"Iqa3", origin, size)) {
  return EXIT_FAILURE;
}
  1. Create the Dart project entry for the desktop runner.
  2. Create the native Windows window wrapper.
  3. Set the initial screen position and size.
  4. Try to create the desktop window.
  5. If creation fails, stop startup immediately.
  6. The window title still says Iqa3, which is a signal that the Windows shell layer has not been fully branded yet.

Aha

When a bug appears only on Windows, do not assume the Dart code is the only place to look. Plugin behavior, runner config, file picking, permissions, and native runner settings may all be part of the root cause.

Module 7

Debugging checklist: where to look first

This is the practical payoff. Use this map when something breaks so you can choose the right file faster.

If the app fails before any screen appears

  • Check lib/main.dart
  • Check setupDependencies()
  • Check service registrations and startup async code

If a route opens the wrong page or bad data

  • Check lib/app/router.dart
  • Check route path parameters
  • Check state.extra usage

If a feature says “service not found”

  • Check lib/core/di/injector.dart
  • Check every dependency in the chain, not only the top cubit
  • Check mock-vs-real repository path

If desktop behavior differs

  • Check Windows runner files
  • Check plugin support on Windows
  • Check file paths and platform-specific packages
